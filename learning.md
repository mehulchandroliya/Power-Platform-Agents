# Power Platform Developer Agent Learnings

## Cross-surface data schema discovery

- Name the project-root schema catalog `power-platform-schema.json`. Preserve that filename for the project so agents and users can find it consistently; the environment name and ID belong inside the file, not in its filename.
- Whenever the schema catalog is created or changed, update its `project.lastUpdated` date.
- On initial project setup, confirm the target app, environment, and data sources/connections, then discover relevant tables, lists, entities, and fields from their metadata or authoring pickers. Record the resulting schema in a durable schema definition under the project directory, following existing project conventions (create a suitable project-local schema file if none exists).
- Include the environment and source identity in the schema definition so it cannot be mistaken for metadata from another environment or connection. Capture the structures the project needs, including logical/display names, columns and types, required fields, and relevant relationships. Apply this across Dataverse, Canvas Apps, model-driven apps, code apps, Power Automate, Power Pages, and other connected sources.
- For later requests in the same project and environment, consult and reuse the project-local schema definition; do not re-fetch or refresh schema on every request. Extend the definition only when the work requires a table/field not already documented.
- Refresh metadata only when a required table or field is missing from the project schema, the user explicitly requests a refresh, or the target environment/source has changed. When the environment or source changes, do not silently reuse incompatible metadata; identify the mismatch and discover the needed schema for the new target.
- Keep discovery requests targeted rather than loading all tables and columns into one response. If metadata cannot be resolved or a name is ambiguous, report the limitation and ask for the missing environment, source, or table detail; never invent logical names, columns, types, or relationships.
- When the project explicitly needs an all-table Dataverse index, query the selected organization's `EntityDefinitions` metadata using authenticated Web API access and select only compact table-level fields such as logical name, schema name, entity-set name, display name, and custom/private flags. Use paging if a next link is returned, record the table count and inclusion scope, and persist the complete index in the project schema file. Do not use a broad connector metadata call that returns huge expanded schemas.
- Keep the scope clear: an all-table index of table definitions is not the same as a full column-and-relationship schema for every table. Retrieve attributes and relationships only for tables required by the project, and mark any uncollected details explicitly rather than implying the schema is complete.

## Power Automate and Dataverse

- For the Dataverse **When a row is added, modified or deleted** operation (`SubscribeWebhookTrigger`), the trigger must be `OpenApiConnectionWebhook`. Operation metadata may report `OpenApiConnection`, but the flow service rejects that trigger type for this webhook.
- Put the trigger fields under `inputs.parameters` using flattened connector keys: `subscriptionRequest/entityname`, `subscriptionRequest/message`, and `subscriptionRequest/scope`. Do not nest them under a `subscriptionRequest` object. Use the table logical name rather than the display label or entity-set plural. For example, the Dataverse Users table is `systemuser`; `systemusers` can fail trigger metadata validation.
- For Dataverse row-change triggers, `message` 1 means add/create, 2 means update, and 3 means delete. `scope` 4 is organization scope.
- A successful save, started state, or raw trigger-definition readback does not prove the Power Automate designer recognizes the trigger's basic-information fields. Verify the selected table and change type in the designer before calling the trigger fixed.
- Before updating an existing flow, preserve and inspect its connection references. If an update or surgical edit fails reference validation, do not repeatedly retry with guessed logical names or replace connector mappings.
- Always prefer updating the existing flow when the user asks to change one. Inspect the flow and use the appropriate update path (`edit_flow` for targeted changes, or preview/update for a full definition); do not create a new flow as a workaround or merely because updating is difficult.
- If the existing flow cannot be updated safely, preserve it, explain the specific blocker, and ask the user before creating a replacement. If a replacement is explicitly approved, verify its designer configuration before switching flows, and ensure the old and replacement flows are not both enabled for the same notification.
- Distinguish a Dataverse `systemuser` row in an environment from creation of an Entra ID directory user; select the event source that matches the user's intended meaning.
